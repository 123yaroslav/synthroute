# Система правил: как она устроена

Правило без проверки остаётся пожеланием. Поэтому правила здесь оформлены как код: у каждого есть ID, уровень,
обоснование и механизм проверки, а скрипт `scripts/check_rules.py` следит за структурой и строит реестр.

## Слои

```
AGENTS.md                ← хаб: миссия, инварианты, карта, индекс правил (читают все агенты)
CLAUDE.md                ← @AGENTS.md + специфика Claude Code
.claude/rules/**/*.md    ← сами правила; frontmatter `paths:` ограничивает область загрузки
.claude/settings.json    ← «зубы»: permissions + хуки (блокировки, автопроверка правил)
.github/, .pre-commit-*  ← «зубы» в CI и при коммите
docs/adr/                ← «почему»: архитектурные решения, на которые ссылаются правила
docs/rules/REGISTRY.md   ← генерируемый реестр всех правил (не править руками)
docs/rules/RETIRED.md    ← выведенные правила; их ID нельзя переиспользовать
```

## Анатомия файла правил

```markdown
---
paths:
  - "backend/**/*.py"          # необязательно; без frontmatter файл грузится всегда
---
# PY — Python-бэкенд           # H1: «ПРЕФИКС — название»; один префикс на файл

> Область и назначение одной строкой.

### PY-001 · MUST · Короткая императивная формулировка
- **Почему:** зачем правило существует (ссылка на ADR, если есть).
- **Проверка:** auto:ci — что именно проверяет CI
- **Исключения:** когда можно отступить (необязательно)
```

Claude Code читает из frontmatter только поле `paths`. Остальные метаданные хранятся в теле файла.

## Поля

| Поле | Значения | Смысл |
|---|---|---|
| ID | `ПРЕФИКС-NNN` | уникален в репозитории и никогда не переиспользуется |
| Уровень | `MUST` | нарушение блокирует мерж |
| | `SHOULD` | отступление допустимо, но его нужно обосновать в PR |
| | `MAY` | рекомендация |
| Проверка | `auto:ci` | проверяется в CI (линтер, скрипт, тест в пайплайне) |
| | `auto:hook` | хук Claude Code или pre-commit блокирует нарушение |
| | `auto:test` | есть юнит- или интеграционный тест |
| | `auto:schema` | гарантируется JSON Schema формата маршрута |
| | `review` | проверяет человек или сабагент `rule-auditor` |
| | `agent` | дисциплина агента, механической проверки нет |

Несколько механизмов объединяются через ` + `. Если автоматизация заявлена, но ещё не реализована,
в конце строки ставится `[todo]`. Скрипт считает такие правила **долгом автоматизации** и показывает его в реестре.

## Жизненный цикл правила

1. **Предложение.** Создайте issue по шаблону `rule-change` или запустите `/new-rule`.
2. **PR.** Изменение правила вместе с механизмом проверки (или `[todo]`) и перегенерированным реестром (`make rules`).
   Если правило архитектурное, к нему прилагается ADR.
3. **Эволюция.** Со временем правило переходит от `review` к `auto:*`: каждую неделю снимайте хотя бы один `[todo]`.
4. **Вывод из оборота.** Удалите правило из файла и добавьте строку в `RETIRED.md` (`- ID — причина, дата`).

## Метрики системы правил

`make rules` печатает число правил по уровням, долю автоматизированных правил (`auto:*` без `[todo]`)
и долг автоматизации. Эти числа стоит включать в недельный отчёт: они показывают инженерную зрелость (критерий защиты 05).
