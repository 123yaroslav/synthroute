# ADR-0002: Генерация, контролируемая верификаторами

- **Статус:** Предложено
- **Дата:** 2026-10-13
- **Связанные правила:** TRUST-001…007, LLM-004, EVAL-003

## Контекст
LLM выдаёт правдоподобные, но неверные маршруты: несбалансированные реакции, несуществующие реагенты, выдуманные ссылки.
Одного запроса к LLM недостаточно, это прямо сказано в ТЗ.

## Решение
Конвейер: **propose → verify → repair → re-verify**.
1. LLM (роли `planner`, `extractor`) предлагает кандидатов только в формате RouteSpec.
2. Детерминированные проверки (`validation/`) выдают диагностики с кодами, по аналогии с линтером.
3. Диагностики возвращаются LLM для ограниченного числа итераций ремонта. Каждая итерация сохраняется как новая версия.
4. Статусы `literature` и `computed` ставит только код. Остальное помечается как `hypothesis` или `failed`.

## Последствия
- Плюсы: главная метрика (доля валидных шагов) измеряется прямо. Цикл ремонта даёт сравнение «до/после» для статьи.
- Минусы: растут стоимость и латентность, поэтому нужны бюджет на прогон и кассеты (LLM-006, LLM-008).
- Дальше: аблации каждой проверки и цикла ремонта (EVAL-007).

## Рассмотренные альтернативы
| Вариант | Почему нет |
|---|---|
| Только LLM + промпт-инжиниринг | не решает галлюцинации и непроверяем |
| Только ретросинтетический движок | нет литературных условий, масштаба и диалога |
| Пост-фильтр без ремонта | теряет кандидатов, которые можно исправить; остаётся как аблация |
